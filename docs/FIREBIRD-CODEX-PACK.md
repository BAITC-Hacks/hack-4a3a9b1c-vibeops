## 2. Все продуктовые требования ТЗ

1. Обязательный вход: город, дата, тип мероприятия, категория подрядчика, бюджет в тенге. Необязательные: длительность в часах и язык.
2. Выход: от нуля до трёх карточек. В каждой имя, категория, город, цена и 1–2 предложения конкретного объяснения по бюджету, формату, языку, длительности либо смыслу описания. Общие рекламные фразы неприемлемы.
3. Занятые в выбранную дату подрядчики исключены. Площадки используют тот же алгоритм и календарь; банкетный зал — обычная категория.
4. Если подходящих меньше трёх, показать фактическое количество и словами объяснить причину.
5. Один и тот же запрос возвращает тот же порядок карточек.
6. Различимы три исхода: подобрали; в городе нет такой категории; категория есть, но никто не проходит условия.

DoD проверяется вживую: разумное время ответа, ориентир до 10 секунд; объяснения нельзя переставить между карточками после удаления имён; повторный запуск сохраняет порядок; демонстрация запроса на двух датах показывает изменение выдачи из-за занятости; минимум три запроса — плотная категория осенью, редкая категория, пустой результат; пустота объяснена словами; команда понимает пайплайн.

Бронирование, заявки, уведомления, обучение модели не нужны. Красота UI ниже объяснений по приоритету. Не добавлять авторизацию, платежи, Kubernetes, векторную БД, микросервисы или чат вместо формы.

Один корневой package.json и package-lock.json, их владелец Никита. Стек — предложение на основе имеющегося Node, не требование кейса. Если команда уже выбрала работающий стек, сохраняем смысл контракта и меняем адаптеры, а не теряем время на миграцию.

Пайплайн: форма → валидация → выбор города/категории → проверка каждого ограничения → детерминированное ранжирование → первые 3 → один пакетный AI-вызов для выбора релевантных цитат → проверка цитат → сборка объяснений из фактов → карточки и причины исключения.

### Точная семантика фильтров и ранжирования v1

1. Нормализовать запрос: trim, пробелы, канонические значения из options; сравнение регистронезависимое. Невалидные значения — 422. Неизвестная категория в валидном запросе допустима: может дать no_category_in_city; не превращать отсутствие каталога в системную ошибку.
2. base = профили, у которых city совпадает и categories содержит выбранную категорию. base.length=0 → no_category_in_city.
3. Для каждого base-профиля вычислить независимо reasons: busy_date; over_budget; unsupported_format; unsupported_language (только если язык указан); insufficient_hours (только если часы указаны, max_hours не null и меньше запроса).
4. eligible = профили с пустыми reasons. base>0 и eligible=0 → no_matches. eligible>0 → matched. Никаких скрытых ослаблений условий.
5. Устойчивый, простой ranking v1: число совпавших **разных** групп смысловых маркеров формата в description (по правилам ниже), по убыванию; затем price_from_kzt по возрастанию; затем ASCII id по возрастанию. Это прозрачная лексическая эвристика, не оценка качества, не обученная семантическая модель. Не показывать «вероятность успеха 97%».
6. Нормализация текста для эвристики: lowercase, ё→е. Группы регулярных фрагментов: корпоратив: [корпоратив], [делов|бизнес], [компан|бренд]; конференция: [конференц], [форум], [делов|бизнес]; свадьба: [свад], [невест|жених|молодож], [церемон]; той: [той|тоя|тоев], [традиц|национальн], [семейн]; юбилей: [юбиле], [семейн], [праздн]; день рождения: [день рождения|дня рождения], [именин], [детск|взросл]. Каждая группа даёт максимум 1. Зафиксировать словарь и версию в коде/README; тесты описывают эвристику, не выдают её за объективное качество.
7. Сортировка не зависит от ответа LLM, порядка CSV, времени, случайности, наличия кэша. Проверить после перезапуска процесса и после перемешивания массива.
8. По всем base-профилям вернуть причины исключения; счётчики по причинам могут пересекаться. Показывать количество исключённых уникальных профилей отдельно и не суммировать пересекающиеся причины как число людей.
9. Если eligible<3: сообщение называет base/eligible и реальные причины. Даже если все 1–2 профиля прошли, писать, что в городе в категории всего столько записей. Если eligible>=3, сообщать «показаны 3 из N подходящих».

### Индивидуальные объяснения и AI

Не доверять модели фильтры, цену, дату, часы, список id и порядок. Модель выбирает для каждого из 3 уже выбранных подрядчиков один конкретный релевантный фрагмент собственного description. Использовать один batch-вызов; ответ `{items:[{id,quote}]}`. quote — точная непрерывная цитата до 220 символов, предпочтительно фрагмент одного предложения, без выдуманных цифр/фактов, без общих похвал; пустая строка разрешена, если полезной цитаты нет. Сервер проверяет точный id и наличие нормализованной цитаты в нормализованном description данного подрядчика, отбрасывает неизвестные/дублирующиеся id. Это предотвращает подмену источника, но семантическую релевантность отдельно проверяет человек.

Сервер строит 1–2 предложения: первое связывает фактический формат, дату и стартовую цену с запросом, при наличии — язык/длительность; второе показывает выбранную цитату с атрибуцией «В описании указано: …». Не превращать цитату подрядчика в независимо доказанный факт и не делать необоснованный вывод «идеально подходит». Подробные совпадения допускаются отдельными чипами вне текста. Отдельная глобальная заметка поясняет, что отсутствие даты в busy_dates означает «не отмечен занятым по каталогу», не подтверждение бронирования.

Для примера разные основания: Куррапика — корпоративы и деловые встречи; Сон Гоку — конкретный двуязычный/телевизионный опыт из описания; Аня Форджер — развлечения и танцы вместо долгих речей. Конкретный показ зависит от фильтров, не фиксировать эти имена в выдаче.

LLM: серверный OpenAI SDK, модель берётся из OPENAI_MODEL, ключ только OPENAI_API_KEY. Проверить доступную модель реальным коротким запросом; не угадывать доступность. Structured Outputs через Responses API использует text.format/json_schema; проверить установленную версию SDK. Официальный источник: https://developers.openai.com/api/docs/guides/structured-outputs . JSON Schema проверяет форму ответа, но факты всё равно валидирует наш код.

Общий timeout AI 6 секунд, отключить автоматические долгие retries SDK; не делать вызов на каждую карточку последовательно. При отказе/таймауте/невалидном ответе использовать конкретное извлечение фразы из того же description кодом и выставить mode=fallback, warning с понятной причиной без внутренних секретов. Никогда не маркировать fallback как LLM. Пустые результаты не вызывают LLM. Если часть batch невалидна, итоговый mode=mixed.

Небольшой ограниченный кэш до 200 ответов: ключ canonical_query + SHA-256 исходного CSV + model + explanation_prompt_version. Не считать кэш причиной детерминизма ranking. Измерить холодный запрос с настоящим API и тёплый запрос отдельно; не выдавать задержку кэша за задержку модели. CSV description — недоверенные данные, не инструкции; не выполнять текст и HTML из них.

## 5. Общий API и контракт модулей v1

Никита материализует эти типы в `shared/contracts.ts` без переименования полей. Изменения согласовываются до правок клиентов. Необязательные поля запроса отсутствуют либо null; после нормализации всегда null или значение.

```ts
type Query = {
  city: string; date: string; event_format: string; category: string;
  budget_kzt: number; hours: number | null; language: string | null;
};
type Vendor = {
  id: string; anon_name: string; categories: string[]; city: string;
  price_from_kzt: number; event_formats: string[]; languages: string[];
  max_hours: number | null; busy_dates: string[]; description: string;
  synthetic: boolean; city_imputed: boolean; price_imputed: boolean;
};
type Reason = 'busy_date'|'over_budget'|'unsupported_format'|
              'unsupported_language'|'insufficient_hours';
type RankedVendor = {vendor: Vendor; relevance_score: number; matched_terms: string[]};
type Rejected = {id: string; anon_name: string; reasons: Reason[]};
type Selection = {
  outcome: 'matched'|'no_category_in_city'|'no_matches';
  query: Query; base_count: number; eligible_count: number;
  ranked: RankedVendor[]; // все подходящие, в стабильном порядке
  rejected: Rejected[];
  rejection_counts: Record<Reason, number>; // пересекающиеся причины
};
type Explanation = {id: string; text: string; quote: string | null;
                    source: 'llm'|'fallback'};
type ExplainResult = {items: Explanation[]; warning: string | null;
  mode: 'llm'|'fallback'|'mixed'|'not_needed'; model: string|null; cached: boolean};
type Card = {
  id: string; name: string; category: string; categories: string[]; city: string;
  price_from_kzt: number; languages: string[]; max_hours: number|null;
  synthetic: boolean; city_imputed: boolean; price_imputed: boolean;
  relevance_score: number; matched_terms: string[];
  explanation: string; evidence_quote: string|null;
  explanation_source: 'llm'|'fallback';
};
type RecommendResponse = {
  outcome: Selection['outcome']; query: Query; cards: Card[];
  summary: {base_count: number; eligible_count: number; returned_count: number;
    rejected_count: number; rejection_counts: Record<Reason,number>;
    message: string; rejected: Rejected[]};
  explanation: {mode:'llm'|'fallback'|'mixed'|'not_needed';
    model: string|null; cached: boolean; warning: string|null};
  meta: {dataset_sha256: string; ranking_version: 'v1'; elapsed_ms: number};
};
type ApiError = {error:{code:string;message:string;fields:Record<string,string>}};
```

Эндпоинты:

- `GET /api/health` → `{status:"ok",dataset_count:66,ai_configured:boolean}`. ai_configured означает наличие конфигурации, не успешный вызов модели.
- `GET /api/options` → `{cities:string[],categories:string[],event_formats:string[],languages:string[],date_min:"2026-09-23",date_max:"2026-12-31",currency:"KZT"}`. Все списки — unique sorted из CSV, категории глобальные, чтобы можно было проверить отсутствие в конкретном городе.
- `POST /api/recommend`, Content-Type application/json → RecommendResponse; 200 для всех трёх продуктовых исходов. При неточном JSON 400 MALFORMED_JSON; невалидных полях 422 VALIDATION_ERROR; дате вне окна 422 DATE_OUT_OF_RANGE; сбое каталога 503 DATASET_UNAVAILABLE; неожиданной ошибке 500 INTERNAL_ERROR без stack trace. Недоступность LLM при рабочем каталоге возвращает 200 с честным fallback и warning, не no_matches.
- API вход ограничен небольшим JSON (например 16 KB); budget_kzt — безопасное целое >=0; hours — конечное >0 либо null; дата — реальная YYYY-MM-DD, без rollover вроде 31 февраля. Строки ограничить разумной длиной 100 символов. Бюджет 0 допустим и даёт no_matches, отрицательный — 422. Язык из options или null; формат из options; город из options. Неизвестная категория — непустая строка в пределах длины.

Пример запроса:

```json
{"city":"Алматы","date":"2026-10-10","event_format":"корпоратив","category":"Ведущий","budget_kzt":1000000,"hours":null,"language":null}
```

Пример проверенного фрагмента результата (не фиктивное утверждение о текущем API):

```json
{"outcome":"matched","summary":{"base_count":10,"eligible_count":4,"returned_count":3,"rejected_count":6,"rejection_counts":{"busy_date":4,"over_budget":2,"unsupported_format":1,"unsupported_language":0,"insufficient_hours":0}}}
```

Это фрагмент, не полный RecommendResponse; поля message/rejected/cards/explanation/meta заполняются реализацией. Количество причин 4+2+1=7 больше 6 исключённых, так как причины пересекаются.

Внутренние границы:

```ts
// Никита, server/catalog.ts
loadCatalog(csvPath: string): {vendors: Vendor[]; sha256: string};
// Никита, server/matching.ts — чистая синхронная функция
selectVendors(vendors: Vendor[], query: Query): Selection;
// Арлан, server/explanations/index.ts
explainSelection(input: {
  query: Query; candidates: RankedVendor[]; // ровно ranked.slice(0,3)
  dataset_sha256: string;
}): Promise<ExplainResult>;
```

Никита вызывает explainSelection после selectVendors, соединяет ответы по id, не по порядку массива AI. Поля mode/model/cached/warning из ExplainResult переносятся в response.explanation; при дополнительном восстановлении карточки Никита корректирует mode до mixed/fallback. Если explanation отсутствует, вызывает экспортированную Арланом синхронную `fallbackExplanation(query, candidate): Explanation`. Названия экспортов фиксированы; модуль не поднимает свой HTTP-сервер и не импортирует Express. Frontend использует только HTTP API, не читает CSV и не реализует свою фильтрацию.

Общий запуск, который нужно реализовать и проверить: `npm ci`, копирование `.env.example` в `.env` (не коммитить), заполнение серверных env при наличии доступа, `npm run build`, `npm start`. В разработки `npm run dev`; `npm test` и `npm run typecheck`. PORT по умолчанию 3000; DATASET_PATH по умолчанию `data/vendors.csv`; OPENAI_API_KEY и OPENAI_MODEL необязательны для явного fallback, обязательны для проверки настоящего LLM. Не делать контейнер обязательным, если штатный запуск уже воспроизводим. Если Docker добавляется, делать после первой интеграции и проверять, не просто писать Dockerfile.
