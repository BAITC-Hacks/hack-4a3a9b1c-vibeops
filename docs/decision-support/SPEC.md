## Поведение

1. Исходные cards, query, outcome, summary и порядок сохраняются. Ответ на исходный запрос никогда не подменяется альтернативой.
2. Предлагать альтернативы только при eligible_count < 3 и base_count > 0. Если категория отсутствует в городе — изменение даты/бюджета её не создаст.
3. За одну альтернативу меняется строго одно поле: date ИЛИ budget_kzt. Город, категория, формат, язык и hours остаются прежними, null остаётся null.
4. Предложение полезно только если число ВСЕХ подходящих профилей выросло. Замена одного на другого при прежнем количестве не считается улучшением этой версии.
5. До двух предложений: одна дата, затем один бюджет. Нет комбинированного изменения даты и бюджета, автоматического увеличения бюджета, смены города или снятия условий.
6. Предложения вычисляются по реальному CSV через существующий selectVendors. Никаких LLM-вызовов на каждую альтернативную дату. Внешний AI используется только для текущих карточек как раньше.
7. Пользователь нажимает кнопку применения — UI подставляет alternative.query и делает обычный POST /api/recommend. Исходный no_matches до нажатия остаётся no_matches.
8. Для 2–3 текущих карточек показывать «Особенности для сравнения» по проверенным цитатам. Без оценки надёжности, превосходства или вымышленных процентов.

## Точный алгоритм Никиты

Сигнатура: buildDecisionSupport(catalog: Catalog, original: Selection, cards: Card[]): DecisionSupport. Допустимо разнести внутренние функции, но публичную точку оставить такой.

### Альтернатива даты

Перебрать UTC-даты исходная ±1…±7 календарных дней, исключая саму дату и даты вне DATE_MIN/DATE_MAX. Для каждой вызвать selectVendors с изменённым date. Оставить только eligible_count > original.eligible_count. Выбрать по: абсолютное смещение дня ASC → eligible_count DESC → строка даты ASC. То есть ближайшая полезная дата, при равенстве лучшая по количеству, затем более ранняя. Не утверждать, что это лучшая дата во всём календаре.

### Альтернатива бюджета

Взять уникальные price_from_kzt > исходного бюджета из профилей того же города/категории, отсортировать по возрастанию. Для каждого порога вызвать selectVendors с изменённым budget_kzt и всеми остальными прежними условиями. Первый результат с большим eligible_count — предложение. Это минимальная стартовая цена, открывающая дополнительный вариант на исходную дату. Занятость, формат, язык, часы нельзя игнорировать. При добавлении только более дорогих занятых профилей предложения быть не должно. Не искать порог по произвольным шагам вроде +10% или +100000.

### Тексты и сравнение — уже готовы

Импортировать describeAlternative и buildComparison из server/explanations/decision-support.ts. describeAlternative(original, proposed) принимает два настоящих Selection и возвращает DecisionAlternative|null; проверяет изменение одного поля и улучшение. Он не ищет минимальный бюджет или ближайшую дату — это обязанность алгоритма выше. new_vendor_ids берутся по разности ВСЕХ eligible ID, не только top-3; ASCII-сортировка. buildComparison(cards) сохраняет порядок карточек, цитату и attribution; для <2 возвращает []. Не дублировать эти функции в backend/UI.

## Ответ API

Источник истины — shared/decision-support.ts. В RecommendResponse добавлено необязательное decision_support: DecisionSupport; после подключения backend возвращать его всегда. Опциональность нужна для постепенной интеграции со старым backend и fixtures, не для скрытия ошибок.

DecisionSupport:
- version: 'v1';
- status: 'available' | 'not_needed' | 'no_category' | 'no_single_change';
- alternatives: DecisionAlternative[];
- comparison: ComparisonItem[];
- message: string|null.

status:
- available: есть >=1 предложение; message=null;
- not_needed: original.eligible_count >=3; alternatives=[], message=null; comparison остаётся;
- no_category: original.base_count=0; alternatives=[], comparison=[], message='Изменение даты или бюджета не добавит эту категорию в каталог города.';
- no_single_change: категория есть, <3, предложений нет; message='Смена только даты в пределах 7 дней или только бюджета не увеличивает число подходящих профилей; остальные условия сохранены.';

DecisionAlternative: kind ('date'|'budget'), query (полный Query), eligible_count, new_vendor_ids, title, explanation, source ('catalog'). Поля «доступен» или confirmed не вводить: речь о календаре каталога, не бронировании.
ComparisonItem: vendor_id, feature, evidence_quote (string|null), source ('llm'|'fallback'|'catalog'). Только ID текущих cards, порядок тот же. Новых LLM-вызовов нет. Если цитата отсутствует, helper показывает факты с source=catalog и честно сообщает отсутствие выделенной особенности.

- Существующие AbortController/sequence должны предотвращать отображение старого результата после быстрого применения другого предложения.
- Не считать скрыто предложенную дату доступной только по title, не реконструировать query из текста.
- При отсутствии decision_support старый интерфейс работает без нового блока. При присутствии проверить структуру в client/src/api.ts; неправильный тип/неизвестная версия — явная ошибка формата, не подмена результата.
- Проверять: <=2 предложения, уникальные kind, kind соответствует единственному изменённому полю, увеличенное количество, непустые/уникальные new_vendor_ids; сравнение ссылается только на текущие cards. Не пересчитывать фильтрацию/доступность на клиенте.
- Для comparison при >=2 entries показать «Особенности для сравнения» с именем существующей cards и feature. Не повторять всю длинную карточку. На узком экране блоки вертикальные.
- Сохранить три исхода, предупреждения AI/fallback, provenance-флаги и цены «от».

## Приёмка новой функции

Никита — реальные unit/HTTP-тесты:
- Дата увеличивает число кандидатов без изменения бюджета/языка/часов; UTC, обе границы календаря, ±7, tie-breaks.
- Бюджет выбирается минимальный; занятый дешёвый кандидат не создаёт ложный порог; несколько кандидатов с одной ценой; все остальные фильтры сохраняются.
- Нет категории / уже >=3 / комбинация двух изменений нужна, но одного недостаточно → правильный status и отсутствие ложных предложений.
- Не мутируются исходный Query, Selection, cards и CSV. Повтор, перемешанный CSV и перезапуск дают те же предложения.
- Применить каждую alternative.query через настоящий /api/recommend: eligible_count совпадает, новые ID действительно входят во все eligible. Карточки всё ещё <=3.
- D1–D6 продолжают проходить; внешних AI-вызовов на перебор альтернатив нет; ориентир времени полного ответа <=10 с.

Нурбол — UI-тесты и настоящий браузер:
- Исходный no_matches остаётся видимым до клика.
- Клик меняет ровно предложенный параметр и отправляет полный Query; hours/language сохранены.
- Повторные клики/смена формы во время запроса не показывают устаревший результат.
- Нет альтернатив → честное сообщение с границами поиска; отсутствующее поле → совместимость со старым ответом.
- Две/три карточки сравниваются в исходном порядке, разные источники явно не выдаются все за AI.

Арлан — проверка смысловой ясности на итоговой интеграции: цифры и новые ID из каталога, цитаты принадлежат профилям, нет обещания бронирования, прирост количества не путается с количеством новых профилей.
