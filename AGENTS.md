# Правила работы агента — VibeOps / HackAlem AI

## Контекст и приоритеты
- Команда из трёх участников. Роли, стек и архитектуру определить по официальному кейсу; не переносить решения прежних тренировок.
- Рабочий репозиторий: `https://github.com/BAITC-Hacks/hack-4a3a9b1c-vibeops`.
- Перед изменениями проверить текущую папку, `git remote -v`, `git status` и ветку; прочитать существующий код и актуальные документы.
- Официальное ТЗ, условия допуска и действующая методика оценки определяют результат. При противоречиях обозначить их; не придумывать критерии или баллы.
- Сначала закрыть обязательный допуск и минимальный сквозной сценарий. Дополнительные функции — после работающего основного сценария.
- Основную функциональность разрабатывать только после официального старта. Предварительные технические заготовки и сторонние компоненты раскрывать по правилам организаторов.

## Командная работа
- До параллельной реализации согласовать роли, владельцев папок, общих файлов и интеграции.
- Зафиксировать общий API/data contract: форматы входа/выхода, ошибки, состояния и способ подключения модулей. Не менять его несогласованно.
- Работать в своей согласованной ветке; для новой ветки агента по умолчанию использовать префикс `codex/`.
- Сохранять чужие и незакоммиченные изменения. Не делать force-push, reset --hard, удаление чужой работы или переписывание истории без явного разрешения.
- Объединять небольшие проверенные изменения через PR в `main`; первую интеграцию проводить рано, не ждать завершения всех частей.
- Самостоятельно выполнять необходимые действия в согласованной зоне. Спрашивать только о существенной недостающей информации, блокерах или изменениях общей договорённости.

## Реализация и проверки
- Выбирать простейшую архитектуру, покрывающую ТЗ. Не добавлять технологии и зависимости без необходимой пользы.
- Mock явно обозначать; он не заменяет обязательную реальную AI/API-функцию. Не имитировать выполненные требования заранее подготовленными ответами.
- После изменений запускать относящиеся к ним проверки; после интеграции проверять полный основной сценарий.
- Проверять некорректный ввод и ошибки/таймауты внешних сервисов, если они используются.
- Перед сдачей проверить установку и запуск в чистой копии строго по README, без неучтённых локальных файлов и ручной правки исходников.
- Подготовить разрешённый способ проверки жюри без личных аккаунтов участников; не публиковать для этого личные ключи.
- В README указывать только реализованные функции, точные команды, конфигурацию, данные, внешние сервисы, предварительные компоненты и известные ограничения.

## Секреты и отчётность
- Не размещать ключи, токены и пароли в коде, Git, логах или чате. Использовать локальное окружение; публиковать только безопасный пример конфигурации.
- Не отправлять закрытые данные внешним сервисам без разрешения организаторов; не выполнять проверки чужой инфраструктуры.
- Отвечать Арлану по-русски, кратко и прямо: сделано → фактически проверено → что осталось или блокирует.
- Не утверждать «работает» без проверки. Различать реальные API-проверки, mock-тесты и непроверенные предположения.
